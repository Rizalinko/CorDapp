# Part 6: Infrastructure as Code

Terraform root: [`terraform/`](../terraform)

## Resources provisioned

| Module | Azure resource | Purpose |
|--------|---------------|---------|
| `networking` | VNet, subnets, NSGs, private DNS zone | Network isolation and routing |
| `acr` | Azure Container Registry | Stores Corda node and CorDapp images |
| `keyvault` | Azure Key Vault | Keystore passwords, DB credentials, TLS certs |
| `aks` | AKS cluster, system + Corda node pools | Kubernetes cluster for the Corda network |
| `postgresql` | PostgreSQL Flexible Server, 3 databases | Node vaults (notary, node1, node2) |

## Network topology

```
VNet: 10.0.0.0/8
  aks-subnet:  10.240.0.0/16   AKS nodes and pods (Azure CNI)
  db-subnet:   10.241.0.0/24   PostgreSQL Flexible Server (delegated)
```

NSG rules on the AKS subnet:

| Rule | Port | Source | Effect |
|------|------|--------|--------|
| `allow-corda-p2p-inbound` | 10200 | VirtualNetwork | P2P between nodes within the VNet |
| `deny-rpc-internet` | 10201 | Internet | Blocks external RPC access |
| `allow-https-inbound` | 443 | Any | Monitoring and management UIs |

Corda P2P between pods within the same AKS cluster is also governed by the
Kubernetes NetworkPolicy defined in the `corda-node` chart (Part 2). The NSG
handles the cloud perimeter; the NetworkPolicy handles pod-to-pod enforcement.

## AKS node pools

| Pool | VM size (dev) | VM size (prod) | Purpose |
|------|--------------|----------------|---------|
| `system` | Standard_D2s_v5 | Standard_D4s_v5 | kube-system, CSI drivers |
| `corda` | Standard_D4s_v5 | Standard_D8s_v5 | Corda node StatefulSets |

The `corda` pool uses managed OS disks (not ephemeral) so that disk pressure
from PVC operations does not affect the OS. Autoscaling is disabled for dev
(fixed `node_count`) and enabled for staging and production.

## Key Vault and Workload Identity

The `keyvault` module creates a Key Vault with RBAC authorization (not access policies)
and purge protection enabled. The `aks` module creates two managed identities:

- `{prefix}-aks-identity`: AKS control plane (assigned to the cluster).
- `{prefix}-corda-wi`: Corda workload identity, federated to the Kubernetes
  ServiceAccount `corda/corda` via OIDC. Pods use this identity to read secrets
  from Key Vault without any credential in the pod spec.

The federation target is `system:serviceaccount:corda:corda`. The AKS CSI
Secrets Provider mounts Key Vault secrets as Kubernetes Secret objects,
making them available to the Helm chart via `existingSecret`.

The PostgreSQL admin password is generated by the `random_password` resource
and written to Key Vault as `postgresql-admin-password` on first apply.
The `lifecycle { ignore_changes = [value] }` block prevents Terraform from
overwriting the secret on subsequent applies (the password is stable once set).

## Multiple environments

Three environment tfvar files and three backend config files cover dev, staging,
and production. Each environment has an isolated state file in the same Azure
Storage Account but under a different blob key:

```
tfstate container:
  dev/corda.tfstate
  staging/corda.tfstate
  prod/corda.tfstate
```

Initializing an environment:
```bash
terraform init -backend-config=environments/dev-backend.tfvars
terraform apply -var-file=environments/dev.tfvars
```

Switching between environments requires re-initializing:
```bash
terraform init -reconfigure -backend-config=environments/prod-backend.tfvars
terraform apply -var-file=environments/prod.tfvars
```

### Why separate state files rather than Terraform workspaces

Terraform workspaces share a backend configuration and differ only in the
state key suffix. The problem for Corda is access control: the team member
running dev applies should not be able to accidentally apply prod state.
Separate state keys in the same container (or separate containers with Azure
RBAC scoped per container) allow you to grant an IAM role read/write access to
`dev/*` only, while prod requires a separate role assignment. Workspaces offer
no such isolation without additional wrapper tooling.

**When to use Terragrunt instead:** if the number of environments or regions
grows (e.g. multi-region active-active or more than three environments),
Terragrunt reduces the duplication of `terraform init + apply` invocations
and the repeated `module` calls in `main.tf`. For three environments it adds
more complexity than it removes.

## Disaster recovery

### AKS and persistent volumes

Corda node PVCs (Azure Disk) are provisioned by the `managed-csi-premium`
StorageClass. Azure Disk does not support cross-zone replication natively.
Options:

1. **Velero with Azure Blob snapshots**: Velero backs up Kubernetes resources
   and creates Azure Disk snapshots on a schedule. Recovery time objective
   depends on snapshot frequency and cluster rebuild time.
2. **Azure Backup for AKS**: native integration; backs up cluster configuration
   and persistent volumes to a Recovery Services Vault. Simpler operational
   model than Velero.

For a bootstrapped private Corda network (no Doorman), losing all node PVCs
requires re-running the bootstrap job and restoring from DB backups. Node
identity keystores are stored in Key Vault secrets (soft-delete + 90-day
retention), so certificate recovery is possible without a full re-bootstrap.

### PostgreSQL

Azure PostgreSQL Flexible Server provides built-in point-in-time restore (PITR)
for the full `backup_retention_days` window (7 days dev, 35 days prod). For
production, `geo_redundant_backup = true` replicates backups to a paired region,
enabling recovery even if the primary region is unavailable.

Restore procedure:
```bash
az postgres flexible-server restore \
  --source-server <server-id> \
  --restore-time <ISO8601-timestamp> \
  --name <new-server-name> \
  --resource-group <rg>
```

After restore, update the DB host in the Helm values and run `helmfile apply`.

### Key Vault

Soft-delete (90 days) and purge protection are both enabled. Deleted secrets
and vaults are recoverable for the full retention period. For production,
enable Key Vault diagnostic logs to an Azure Monitor workspace so that all
secret access is auditable.

### Terraform state

The state storage account has blob versioning enabled (see `bootstrap-state.sh`).
Accidental state corruption can be recovered by restoring a previous blob version
via the Azure Portal or `az storage blob restore`.

## First-time setup

```bash
# 1. Create the state storage backend (once per subscription).
bash terraform/scripts/bootstrap-state.sh

# 2. Initialise and apply for the target environment.
cd terraform
terraform init -backend-config=environments/dev-backend.tfvars
terraform apply -var-file=environments/dev.tfvars

# 3. Configure kubectl.
$(terraform output -raw aks_get_credentials)

# 4. Annotate the corda ServiceAccount for Workload Identity.
kubectl annotate serviceaccount corda \
  -n corda \
  azure.workload.identity/client-id=$(terraform output -raw corda_workload_identity_client_id)
```
