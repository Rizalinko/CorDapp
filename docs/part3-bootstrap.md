# Part 3: Deploying a Basic Corda Network

Chart: [`charts/corda-bootstrap`](../charts/corda-bootstrap)
Helmfile: [`deploy/helmfile.yaml`](../deploy/helmfile.yaml)

## Tooling choice

**Helmfile.** Ausgang orchestrates multiple Helm releases by calling Helm directly
inside CI pipelines, with per-environment value files beside each chart. Helmfile
is the closest non-Bazel equivalent: it is a declarative manifest of Helm releases
that supports per-release dependency ordering via `needs`, merged value layers, and
a single `helmfile apply` entry point. The releases in `deploy/helmfile.yaml` map
one-to-one to the Helm `helm upgrade --install` calls an engineer would write by
hand, which keeps the abstraction thin and auditable.

## Network topology

```
Kubernetes namespace: corda
                                              +---------------------------------+
                                              |  corda-bootstrap Job            |
                                              |  init: corda-bootstrapper.jar   |
                                              |  main: kubectl publisher        |
                                              |  outputs:                       |
                                              |    Secrets  corda-*-certs       |
                                              |    Secrets  corda-*-secrets     |
                                              |    ConfigMap corda-network-params|
                                              +-----------+---------------------+
                                                          |  (must complete first)
                          needs                           v
+-----------------------------+        +-----------------------------+
|  StatefulSet: notary        |  P2P   |  StatefulSet: node1         |
|  (non-validating notary)    |<------>|  (AcmeCorp counterparty A)  |
|  Service: notary-*-p2p      |        |  Service: node1-*-p2p       |
|  Service: notary-*-rpc      |        |  Service: node1-*-rpc       |
+-----------------------------+        +-----------------------------+
             ^                                        ^
             |               P2P                      |
             +<------------->+------------------------+
                             |  StatefulSet: node2         |
                             |  (AcmeCorp counterparty B)  |
                             |  Service: node2-*-p2p       |
                             |  Service: node2-*-rpc       |
                             +-----------------------------+

All nodes mount the same ConfigMap (corda-network-params) which contains:
  network-parameters  (one file, shared across all nodes)
  nodeInfo-<hash>     (one file per node, used for peer discovery)
```

## The chicken and egg problem

Corda nodes cannot start without:

1. A network trust root and `network-parameters` file (establishes the rules of the network)
2. The `NodeInfo` of every other participant (so peers can find each other)

But `NodeInfo` files are generated by running the node, which cannot start without them.

**Solution:** the Corda network bootstrapper (`corda-bootstrapper.jar`) breaks the cycle.
It reads a minimal `node.conf` (just `myLegalName` and `p2pAddress`) for each node and
generates all certificates, `network-parameters`, and `NodeInfo` files **offline**,
before any node starts. This is the same pattern used in the compose network (Part 1):
the `bootstrap` service completes first, then the node services start.

For Kubernetes, the bootstrapper runs as the init container of a Job in the
`corda-bootstrap` chart. A publisher container in the same Job pod uploads the
outputs to Kubernetes Secrets (keystores) and a ConfigMap (network-parameters plus
NodeInfo files). The node releases all declare `needs: corda/corda-bootstrap` in
Helmfile, so Helmfile waits for the Job to complete (`waitForJobs: true`) before
deploying the node StatefulSets.

**Order of operations:**

```
helmfile apply
    |
    +-- 1. Deploy corda-bootstrap release
    |       a. RBAC (ServiceAccount, Role, RoleBinding)
    |       b. ConfigMaps (node.conf inputs, shell scripts)
    |       c. Secret (bootstrap passwords)
    |       d. Job starts
    |           init container: corda-bootstrapper.jar
    |               reads   /nodeconfs/{notary,node1,node2}.conf
    |               writes  /bootstrap/{node}/certificates/*.jks
    |                       /bootstrap/network-parameters
    |                       /bootstrap/{node}/additional-node-infos/nodeInfo-*
    |           main container: publisher (kubectl)
    |               creates Secrets  corda-{notary,node1,node2}-certs
    |               creates Secrets  corda-{notary,node1,node2}-secrets
    |               creates ConfigMap corda-network-params
    |       e. Helmfile waits for Job completion
    |
    +-- 2. Deploy notary, node1, node2 (in parallel, after bootstrap)
            Each StatefulSet:
                init: materialize-certs   mounts cert Secret onto PVC
                init: materialize-netparams mounts network-params ConfigMap onto PVC
                main: corda node starts
```

## How node identities and certificates are distributed

The bootstrapper generates one set of keystores per node:

| File | Content |
|------|---------|
| `nodekeystore.jks` | Node legal identity keypair and certificate chain |
| `sslkeystore.jks` | TLS keypair for P2P traffic |
| `truststore.jks` | Network trust root (same for all nodes) |

These are published as a Kubernetes Secret per node (`corda-notary-certs` etc.).
The `materialize-certs` init container in `corda-node` copies them from the Secret
onto the PVC's `certificates/` directory before the node process starts.

The `corda-network-params` ConfigMap contains `network-parameters` and one
`nodeInfo-<hash>` file per node. The `materialize-netparams` init container copies
them onto the PVC. Corda reads `nodeInfo-*` files from `additional-node-infos/` at
startup to learn its peers' addresses and public keys.

## Adding a new node

1. Add the new node's entry to `deploy/bootstrap/values.yaml` under `nodes`.
2. Delete the existing bootstrap Job so the bootstrapper re-runs:
   ```
   kubectl delete job corda-bootstrap-corda-bootstrap-bootstrapper -n corda
   ```
3. Run `helmfile apply` again. The bootstrapper regenerates all NodeInfos and
   `network-parameters` with the new participant included. The existing node
   PVCs are updated by the `materialize-netparams` init containers on the next
   pod restart.
4. Add a new Helm release for the new node in `deploy/helmfile.yaml` with its own
   `values.yaml` and `values.prd.yaml`, with `needs: [corda/corda-bootstrap]`.
5. Run `helmfile apply`.

Note: adding a node changes the `network-parameters` file (it contains a hash of
all NodeInfos). Existing nodes must restart to pick up the updated ConfigMap. In a
production network with Doorman and Network Map Service, this process is automated
and does not require restarting existing nodes.

## Network parameter updates

`network-parameters` is a signed file that governs platform version requirements,
max transaction size, notary list and similar settings. Updating it requires all
nodes to agree.

**In a bootstrapped private network (our setup):**

1. Update the relevant field in the bootstrapper input (e.g. `minimumPlatformVersion`).
2. Re-run the bootstrapper (delete the bootstrap Job, then `helmfile apply`).
3. The new `corda-network-params` ConfigMap is applied. On the next pod restart,
   the `materialize-netparams` init container copies the updated file onto each
   node's PVC. Corda accepts the update automatically in a dev bootstrapped network.

**In a production network with Doorman and Network Map Service:**

1. The network operator signs the new `network-parameters` using the root key.
2. The NMS publishes the update. All nodes download it automatically.
3. Each node logs a prompt for the operator to accept the update via `run acceptNewNetworkParameters()` over RPC.
4. After all nodes accept, the new parameters take effect at the agreed deadline.

## Running locally on Kind

Prerequisites: `kind`, `kubectl`, `helm`, `helmfile`

```bash
make k8s-up      # create Kind cluster + helmfile apply (bootstrap + 3 nodes)
make k8s-down    # helmfile destroy
make k8s-cluster-down  # destroy + delete Kind cluster
```

Or run Helmfile directly:

```bash
kind create cluster --name corda-local
kubectl config use-context kind-corda-local
helmfile -f deploy/helmfile.yaml apply
```

Watch startup (first boot takes up to 10 minutes on Kind):

```bash
kubectl -n corda get pods -w
kubectl -n corda logs -f statefulset/notary-corda-node
```
